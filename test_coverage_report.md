**2026-08-03 `ear_clipping_triangulation` — critical bug: infinite loop on a collinear vertex at the ring's start.** The user added `detail::view::are_collinear()` to correctly handle a vertex that's neither reflex nor a valid ear because it's exactly collinear with its two neighbors (a degenerate "straight angle" — e.g. a redundant point sitting on the middle of an otherwise-straight edge). **2026-08-05 mesh-conformity checking — `validate_adjacency()`/`fix_adjacency()`, new `AdjacencyConformity`, batch `triangulate(vector<Polygon2D>, ...)`.** New rule enforced across the mesh family: "every edge has at most 1 neighbor" — no facet vertex may lie in the interior of another facet's edge, only exactly at that edge's own start/end vertex (the standard "conforming mesh"/no "hanging nodes" (FEM) / no "T-junctions" (graphics) / valid-PSLG (mesh generation) rule). ## Key Takeaways

- **`fix_adjacency(Polygon2D/3D)` redesigned from splice-only to a real facet split (2026-08-05).** The original implementation repaired a T-junction by splicing the foreign vertex into the coarse facet's ring as an extra flat (180°) vertex — same outline, same area, no new facet. User feedback on the doc picture: this is *invisible* — a flat vertex added to a dead-straight edge doesn't change how the polygon renders at all, so the "before"/"after" panels looked identical apart from a vertex-color trick. Redesigned to actually cut the coarse facet in two: after splicing, a diagonal is cut from the spliced vertex to its nearest ring vertex that forms a valid non-self-intersecting diagonal (checked via proper-segment-intersection against every other edge, plus a winding-number interior test on the diagonal's midpoint) — the standard "diagonal-to-nearest-vertex" polygon-splitting technique, chosen over an initially-considered perpendicular-sweep-cut alternative because it's provably valid for *any* simple polygon (convex or not), whereas perpendicular cuts are only well-defined on convex facets and risk thin slivers. Trade-off accepted knowingly: since it cuts to the *nearest* vertex rather than straight across, splitting a rectangle with multiple T-junctions on one edge produces an irregular mix of triangles/quads, not tidy rectangular strips — this was explicitly discussed and chosen over the messier-but-still-correct alternative. `fix_adjacency(Triangle2D/3D)` was unaffected (already re-triangulates via ear-clipping, which is diagonal-cut-based already). One nice side effect: the batch `triangulate(vector<Polygon2D>, Enforce, ...)` overload no longer needs to force `Collinearity::Guaranteed` on `fix_adjacency`'s output, since a genuinely split facet has no leftover flat vertices to protect from being stripped.
- **A real ear-clipping bug found while testing `fix_adjacency(vector<Triangle2D/3D>)` (2026-08-05).** Both `ear_clipping_triangulation()` and `ear_clipping_best_fit_triangulation()` scan only *reflex* vertices as potential ear-blockers (a standard, normally-valid optimization: in a proper simple polygon, a non-reflex vertex can never lie inside another vertex's candidate ear). That assumption breaks for an exactly-flat (180°) vertex, which is neither reflex nor a valid ear itself, but — unlike a true interior point — can sit exactly on a candidate ear's boundary edge, where `is_point_in_triangle`'s inclusive boundary test would have caught it, if it had ever been scanned. It wasn't, so a candidate ear could wrongly "swallow" the flat vertex whole, silently dropping the two edges either side of it from the triangulation. Only reachable under `Collinearity::Guaranteed` fed a genuinely collinear ring — exactly `fix_adjacency`'s own re-triangulation path for a facet whose splice grew it past 3 vertices, and previously untested because earlier `fix_adjacency` tests only checked total area (which a degenerate zero-area sliver doesn't perturb), never post-fix `validate_adjacency()`. Fixed by treating flat vertices as ear-blockers alongside reflex ones in both functions; regression-tested via `FixAdjacency_TriangleTJunction_ReTriangulatesAndPreservesTotalArea` (2D and 3D) and the pre-existing `EarClippingTriangulation_CollinearMidEdgeVertex_ProducesCorrectAreaAndCount` test, which was passing by coincidence before (ear order happened to avoid the bug) and is now correct by construction.
- **Zero stubs remain.** The prior stub cluster (`Polygon2D/3D::DistanceTo`, `Triangle2D::DistanceTo`/`Intersects(△)`/`Intersection(△)`, `Triangle3D::DistanceTo`) is fully implemented; `Polygon2D::FromWkt`'s broken-result bug is fixed. The remaining action is writing Python/C# tests for the four `DistanceTo(Point)` methods — not yet done, still the single biggest concrete gap left.
- **`Vector2D`'s C++ gap is closed**: `Length`, `Normalize`, `AlmostEquals`, `ToPoint`, `BasisY` are now directly tested in `test_vector2d.cpp`.
- **`Polygon2D/3D::ConvexHull()` (the member method) is now directly tested in C++** — 4 tests each (already-convex, concave-drops-the-dent, hole-ignored, result-`IsConvex()`), closing a gap the previous report had mismarked as already covered.
- **C#'s `ToString()`/`operator==` systemic gap is closed**: all 26 bound classes now have a `ToString()` test, and all 20 classes missing `operator==` (everything except the 5 that already had it: `Vector2D`, `BBall2D/3D`, `BRect2D`, `BPrism3D`) now have one — `WktParser` correctly has neither `==` test added (it has no `operator==` binding, not a gap). C# overall coverage moved from ~78% to ~87%. The polyline-overload family (`Overlaps`/`Touches` against `Polyline2D/3D`) remains the biggest *remaining* C# gap, thin across `Line`/`Ray`/`LineSegment`.
- **`Vector3D` operators are now fully tested in Python** (`__add__`/`__sub__`/`__mul__`/`__rmul__`/`__truediv__`/`__neg__`/`__eq__` via `test_arithmetic`/`test_negation`/`test_eq`, mirroring `Vector2D`'s existing `test_arithmetic`). C# still lacks `ToWkt`/`ToFile`/`FromFile`/`Perp`/`IsParallel` for `Vector3D` (unrelated to the operator gap, out of scope for this pass).
- **Free functions are the best-covered surface across all three languages**: all 28 Python free functions and all 20 C# `GeomUtil` wrappers have ≥1 test; the C++ public wrappers (`has_intersections`, `find_intersections`, decimation, boolean ops, `clip`, Bezier smoothing, polyline expansion, extreme points, `distance_to`, `tangents_to`) are likewise fully covered — only the internal `detail::` sweep-line/hull primitives lack *direct* by-name tests (they're exercised transitively).
- **`WktParser` is thin in C++** — only 1 `TEST_F` in the entire file, with `GetFilePath` untested; Python and C# cover it more thoroughly (C# now fully, 6/6).
- **No class is at 0%.**
- **`Mesh2D/3D`, `PolyMesh2D/3D`, `GridCell2D/3D` are now fully validated, tested, and bound** in all three languages, closing what was previously the only untested/unbound surface in the library. This pass found a **critical off-by-one bug** in the shared vertex-welding logic (every mesh with ≥2 faces sharing a vertex would have wrong-by-one indices and an out-of-bounds read on the last unique vertex) plus three smaller bugs (a namespace-qualification compile error, a dead non-returning function, and a missing hole-rejection check) — see the dated note above for details. All four are covered by dedicated regression tests in C++, Python, and C#.
- **Verifying these passes surfaced build-breaking bugs unrelated to the immediate task** — 4 in the mesh WIP code during the first gap-filling pass (missing braces, duplicate declarations), then the off-by-one and 3 more during the mesh validate-and-expand pass itself — all fixed as a side effect of forcing a real rebuild rather than trusting a stale cache, consistent with the standing "force a rebuild before trusting results" lesson.
