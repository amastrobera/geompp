**2026-08-03 `ear_clipping_triangulation` — critical bug: accepted diagonals that exit the polygon.** Found while building a visual-doc example: an L-shaped hexagon `(0,0),(4,0),(4,2),(2,2),(2,4),(0,4)` triangulated into 4 triangles whose *areas summed correctly* (12, matching the polygon) but one triangle — `(0,4),(4,0),(4,2)` — extended outside the polygon through the notch, while another shrank to compensate; the area check alone didn't catch it because the errors canceled. Root cause: the ear-validity check (`lambda_is_point_in_triangle`, `calc_utils2d.cpp`) used a *strict* left-turn test, so a reflex vertex sitting exactly *on* a candidate ear's diagonal — not just strictly inside it — was invisible to it. This polygon's reflex vertex `(2,2)` happens to be exactly collinear with the non-adjacent vertices `(0,4)` and `(4,0)` (all three satisfy `x + y = 4`), so the algorithm accepted `(0,4)-(4,0)` as a valid diagonal even though the vertex sitting on top of it should have disqualified it. This is a general hazard, not specific to this one shape: any polygon where a reflex vertex is exactly collinear with two non-adjacent vertices can trigger it, which is why the original test suite (a chevron with one reflex vertex in general position) never caught it. Fixed by making the point-in-triangle test inclusive (`>= 0` instead of `> 0`), so a boundary-touching point disqualifies the ear same as a strictly-interior one; verified against the full existing suite (no regressions) plus new tests asserting every produced triangle's centroid is contained in the source polygon, not just that areas sum correctly. This is a single shared template function (`View2D`-projected, used by both 2D and 3D triangulation), so the fix covers `Polygon2D/3D::Triangulate()`, `PolyMesh2D/3D::Triangulate()`, and the free `triangulate()` in one place. New tests: +2 C++ (`test_calc_utils2d.cpp` direct `ear_clipping_triangulation` call, `test_polygon2d.cpp` public API — both assert per-triangle containment, not just total area), +1 Python, +1 C#.

**2026-08-03 `ear_clipping_triangulation` — critical bug: infinite loop on a collinear vertex at the ring's start.** The user added `detail::view::are_collinear()` to correctly handle a vertex that's neither reflex nor a valid ear because it's exactly collinear with its two neighbors (a degenerate "straight angle" — e.g. a redundant point sitting on the middle of an otherwise-straight edge). The first attempt didn't compile at all (`are_collinear(p_prev, p_cur, p_next)` — the function needs a 4th `View2D const&` argument). The next attempt compiled but introduced a deeper bug: an early `i = i_next; continue;` skip-branch bypassed the loop's normal bottom-of-iteration update (`i_prev = prev_id[i]; i_next = next_id[i];`), leaving `i_prev`/`i_next` stale — still describing the *old* `i`'s neighbors. When the ring happens to start (`i == 0`) on a collinear vertex, this can make `i_next == i` on the very next iteration, and the loop spins forever re-checking the same self-referencing degenerate triangle — confirmed by hand-trace and then empirically: a direct test hung for 8+ seconds (had to be killed). The user's final fix restructures the loop so the collinear check *gates* whether the ear-check-and-clip logic runs (`if (!are_collinear(...)) { ...ear check... }`), instead of an early `continue` past the update — every iteration now reaches the single bottom-of-loop `i`/`i_prev`/`i_next` update exactly once, eliminating the stale-index bug class structurally rather than patching around it. Verified the star-polygon example from the visual doc is unaffected either way (it has no collinear vertices, so this code path never triggers for it) — same 8-triangle fan, all valid, before and after. New tests: +2 C++ (`test_calc_utils2d.cpp`: a redundant mid-edge vertex, and the same shape rotated so the collinear vertex is at ring-start — the exact hang case), +2 Python, +2 C#, all via `TriangulationCollinearity.Guaranteed` so the redundant point survives into `ear_clipping_triangulation` instead of being stripped by `Enforce` beforehand.

**2026-08-03 exact-tiling and hanging-vertex checks for `Polygon2D::Triangulate()` (5-pointed star).** Asked to prove the star example's triangulation is a true exact tiling (not just area-sum-equal, which can't rule out a positive-area overlap on one side canceled by a gap elsewhere) and to check for "hanging" vertices (an original polygon vertex landing in the *middle* of a triangle edge instead of being a shared corner — a T-junction, a real defect class distinct from area/overlap). Both checks came back **clean for every tested shape** (convex quad, chevron, L-shape, 5-pointed star) in all three languages — no overlaps, no gaps, no hanging vertices. Implementation notes:
- **No-overlap + full-coverage** was first attempted via `Polygon2D::Union()`/`Xor()` (union all triangles, XOR against the original polygon, expect zero leftover area) but that surfaced a **separate, real bug**: `Union()` mis-clips when the two operands share a full edge (not just an overlapping region) — confirmed with two star-derived polygons sharing edge `(3.71,3.97)-(0.15,3.93)`: instead of merging into one pentagon, it returned 2 disconnected pieces and silently dropped a vertex, shrinking one piece's area (1.4413 vs the correct 1.4697). Not fixed (out of scope here, flagged for its own pass) — worked around instead with pairwise `Triangle2D::Intersection()` (no positive-area overlap) plus a dense, edge-margin-excluding sampling grid (`Polygon2D::Contains()` and "inside some triangle" must be the same set of points away from any edge).
- The grid-sampling check needed an edge-exclusion margin (0.02, found by trial): an un-margined first pass found 8/9409 "mismatches," all within 0.0022 units of a boundary — `Polygon2D::Contains()` and `Triangle2D::Contains()` use different algorithms (winding number vs. barycentric) and can disagree right at a shared edge, which is boundary-inclusion noise, not a real gap/overlap.
- Found (Python/C# only) that **`Triangle2D::Intersection(Triangle2D)` isn't bound** in either language — only the `Line2D` overload is. Worked around via `ToPolygon().Intersection()` (which is bound); not fixed, flagged separately.

**2026-08-03 `Triangle2D::Intersects`/`Intersection` — missing `Ray2D`/`LineSegment2D`/`Triangle2D` overloads in Python and C#.** Confirmed as "something we forgot": `Triangle3D` has the *full* set of `Intersects`/`Intersection` overloads (`Line`/`Ray`/`Segment`/`Plane`/`Triangle`) bound in both Python and C#, but `Triangle2D` — despite implementing and C++-testing all 4 overloads (`Line2D`/`Ray2D`/`LineSegment2D`/`Triangle2D`, see `test_triangle2d.cpp`'s `IntersectionWLine`/`WRay`/`WSegment`/`WTriangle`) — only ever had the `Line2D` overload bound in either language. Bound the missing 3 in both, mirroring `Triangle3D`'s exact pattern (including the `intersects_triangle` Python name for the self-type overload, matching the existing convention for disambiguating same-type overloads under pybind11). While rebuilding to verify, also caught a genuine compile error in the user's own in-progress edit to `are_collinear()` (`calc_utils2d.cpp`): `double[x0, y0] = view.xy(p0);` isn't valid C++ — a structured binding can only be declared `auto`, not a concrete type. `View2D::xy()` (returning `std::pair<double,double>`) does exist as intended; fixed the declaration to `auto [x0, y0] = view.xy(p0);`. New tests: +7 C# (`Intersects_Line2D_CutsInterior_True` plus 6 more covering `Ray2D`/`LineSegment2D`/`Triangle2D`, hit and miss cases each — this whole area had *zero* prior C# tests, binding gap and test gap together), +3 Python (`test_intersection_with_ray`, `test_intersection_with_segment`, `test_intersects_and_intersection_with_triangle`).

**2026-08-03 comb-polygon stress test and edge-manifold check for `Triangulate()`.** Two more asks against the triangulation work: (1) add the "comb" polygon (3 tall teeth separated by deep, narrow notches — the classic adversarial shape for naive ear-clipping) as a permanent test, since it had only existed as an ad-hoc validation script; (2) add a check that every triangle edge is edge-manifold — each oriented "half-edge" either has no twin (a polygon boundary edge) or exactly one twin in another triangle traversing the same undirected edge in the *opposite* direction (`twin.start == edge.end && twin.end == edge.start`), the standard consequence of consistent CCW winding across all triangles. The user expected the manifold check to fail on the 5-pointed star based on visual inspection of the doc picture. Computed rigorously (not by hand): **zero violations**, across all 24 of the star's half-edges and every other test shape (L-shape, chevron, comb) too — the visual impression came from many thin triangles sharing one common *vertex* (the fan hub), which looks like overlapping edges in a cluttered rendering but isn't a twin-matching defect (that requires two full shared endpoints, not just a coincident vertex). Also confirmed a narrower, correct claim the user made about `next_id[i_prev] = i_next; prev_id[i_next] = i_prev;` (`calc_utils2d.cpp:2418-2419`): a *clipped* vertex is provably never revisited, since nothing in the chain can ever produce it as `i_next` again once spliced out — distinct from (and not contradicted by) the separate, real phenomenon that a still-active vertex can be rejected then later re-checked and clipped, demonstrated with the comb polygon itself (vertex 1: rejected, then clipped after 6 unrelated clips elsewhere). New tests: +2 C++ (`EarClippingTriangulation_CombPolygon_RequiresMultipleTraversalLaps` direct `detail::view` call, `Triangulate_CombPolygon_ProducesCorrectAreaAndCount` public API), plus a new `ExpectHalfEdgesAreManifold` helper retrofitted into all 5 existing `Polygon2D::Triangulate()` shape tests (convex quad, chevron, L-shape, both star tests); +1 Python, +1 C# (comb polygon, mirrored with both existing helper checks plus the new manifold check). Added a comb-polygon before/after picture to the visual doc, alongside the star's.

## Key Takeaways

- **Zero stubs remain.** The prior stub cluster (`Polygon2D/3D::DistanceTo`, `Triangle2D::DistanceTo`/`Intersects(△)`/`Intersection(△)`, `Triangle3D::DistanceTo`) is fully implemented; `Polygon2D::FromWkt`'s broken-result bug is fixed. - **C#'s `ToString()`/`operator==` systemic gap is closed**: all 26 bound classes now have a `ToString()` test, and all 20 classes missing `operator==` (everything except the 5 that already had it: `Vector2D`, `BBall2D/3D`, `BRect2D`, `BPrism3D`) now have one — `WktParser` correctly has neither `==` test added (it has no `operator==` binding, not a gap). C# overall coverage moved from ~78% to ~87%. The polyline-overload family (`Overlaps`/`Touches` against `Polyline2D/3D`) remains the biggest *remaining* C# gap, thin across `Line`/`Ray`/`LineSegment`.
- **`Vector3D` operators are now fully tested in Python** (`__add__`/`__sub__`/`__mul__`/`__rmul__`/`__truediv__`/`__neg__`/`__eq__` via `test_arithmetic`/`test_negation`/`test_eq`, mirroring `Vector2D`'s existing `test_arithmetic`). - **Free functions are the best-covered surface across all three languages**: all 28 Python free functions and all 20 C# `GeomUtil` wrappers have ≥1 test; the C++ public wrappers (`has_intersections`, `find_intersections`, decimation, boolean ops, `clip`, Bezier smoothing, polyline expansion, extreme points, `distance_to`, `tangents_to`) are likewise fully covered — only the internal `detail::` sweep-line/hull primitives lack *direct* by-name tests (they're exercised transitively).
